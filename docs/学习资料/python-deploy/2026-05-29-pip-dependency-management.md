## 一、依赖管理的三层演进

### 1.1 原始时代：`requirements.txt` 全量冻结

```bash
# 传统做法 — pip freeze 直接导出所有包
pip freeze > requirements.txt

# 问题：
# ① 混合了主依赖 + 传递依赖，无法区分"我要的"和"它带的"
# ② 无法追踪"谁引入了这个包"
# ③ 升级一个包可能级联破坏整个依赖树
```

**典型症状**：`requirements.txt` 写了 5 个包名，但 `pip list` 显示几十个。不知道哪些可以删。

### 1.2 现代方案 A：`pip-tools` (声明式 + 锁定)

```
requirements.in（人工维护）→ pip-compile → requirements.txt（自动生成）→ pip-sync → 环境
```

| 文件 | 维护方式 | 内容 | 示例 |
|------|----------|------|------|
| `requirements.in` | 手动编辑 | 仅顶层依赖，宽松约束 | `flask>=2.0`, `requests` |
| `requirements.txt` | **自动生成，勿手动改** | 所有依赖精确版本 + 来源注释 | `certifi==2024.8.30  # via requests` |

### 1.3 现代方案 B：`uv` (一体化替代)

```bash
uv init                    # 生成 pyproject.toml
uv add flask requests      # 添加顶层依赖（写入 pyproject.toml）
uv lock                    # 生成 uv.lock（含哈希）
uv sync                    # 同步到 .venv
uv run python main.py      # 在管理环境中执行
```

**uv vs pip-tools 对比**：

| 维度 | pip-tools | uv |
|------|-----------|-----|
| 速度 | 较慢（纯 Python） | 快 10-100x（Rust） |
| 功能 | 仅依赖锁定 | 锁定 + venv + 版本管理 + 项目创建 |
| 跨平台锁文件 | ✅ 优势 | ⚠️ pip lock 绑定当前平台 |
| 成熟度 | 生产验证多年 | 快速迭代中（2026年已非常成熟） |
| **推荐场景** | 需要 cross-platform requirements.txt | 新项目 / 我们的环境 |

## 二、pip-tools 工作流详解

### 2.1 安装

```bash
# 在任意虚拟环境中安装（不装全局）
python3 -m venv .tools-env
source .tools-env/bin/activate
pip install pip-tools
```

### 2.2 pip-compile — 依赖解析与锁定

**基本用法**：

```bash
# 从 requirements.in 生成 requirements.txt
pip-compile requirements.in

# 从 pyproject.toml 生成（PEP 621）
pip-compile pyproject.toml
```

**关键参数**：

| 参数 | 功能 | 使用场景 |
|------|------|----------|
| `--upgrade` | 强制重新解析全部依赖 | 定期全面升级时 |
| `--upgrade-package <pkg>` | 仅更新指定包 | 安全地单包升级 |
| `--upgrade-package 'pkg<3.0'` | 更新到满足约束的最新版 | 有上限的升级 |
| `--generate-hashes` | 为每个包生成 SHA256 哈希 | 安全审计 / CI/CD |
| `--output-file <file>` | 自定义输出路径 | 多环境分离 |
| `-` (stdout) | 输出到标准输出 | 管道操作 |

**生成的 requirements.txt 示例**：

```
#
# This file is autogenerated by pip-compile with Python 3.13
# To update, run: pip-compile requirements.in
#
blinker==1.9.0           # via flask
certifi==2024.8.30        # via requests
charset-normalizer==3.4.0 # via requests
click==8.1.7             # via flask
flask==3.1.0             # via -r requirements.in
requests==2.32.3         # via -r requirements.in
urllib3==2.2.3           # via requests
werkzeug==3.1.3          # via flask
```

### 2.3 pip-sync — 环境同步

**关键区别于 `pip install -r`**：pip-sync **会移除**不在锁文件中的多余包。

```bash
# 基本同步
pip-sync requirements.txt

# 同步多组需求（如生产+开发）
pip-sync dev-requirements.txt requirements.txt

# 传递 pip 参数
pip-sync requirements.txt --pip-args '--no-cache-dir'
```

### 2.4 完整工作流

```
┌──────────────────────┐
│   requirements.in    │ ← 手动编辑：声明"我需要什么"
│   pyproject.toml     │ ← 或用 PEP 621 格式
└──────────┬───────────┘
           │ pip-compile
           ▼
┌──────────────────────┐
│  requirements.txt    │ ← 自动生成：精确版本 + 来源注释
│  （纳入版本控制）      │
└──────────┬───────────┘
           │ pip-sync
           ▼
┌──────────────────────┐
│  Python 环境          │ ← 精确匹配，无多余包
└──────────────────────┘
```

**日常操作清单**：

| 操作 | 命令 |
|------|------|
| 初始化项目 | 编辑 `requirements.in` → `pip-compile requirements.in` → `pip-sync requirements.txt` |
| 添加新包 | 编辑 `.in` 追加 → `pip-compile requirements.in` → `pip-sync requirements.txt` |
| 升级单个包 | `pip-compile --upgrade-package flask requirements.in` → `pip-sync` |
| 全面升级 | `pip-compile --upgrade requirements.in` → `pip-sync` |
| CI/CD 部署 | `pip-sync requirements.txt`（确定性还原） |
| 安全审计 | `pip-compile --generate-hashes requirements.in` |

### 2.5 多环境分离（生产/开发）

```bash
# base.in — 生产依赖
django>=4.0
gunicorn

# dev.in — 开发依赖（引用基础）
-r base.in
pytest
black
ruff

# 分别编译
pip-compile base.in --output-file requirements.txt
pip-compile dev.in --output-file dev-requirements.txt

# 生产只同步基础依赖
pip-sync requirements.txt
# 开发同步全部
pip-sync dev-requirements.txt requirements.txt
```

## 三、依赖树分析工具：`pipdeptree`

当面对一个混乱的旧项目时，第一步是搞清楚依赖关系。

```bash
# 安装
pip install pipdeptree

# 查看完整依赖树（缩进=传递依赖）
pipdeptree --warn silence

# 反向查询：谁依赖了 numpy？
pipdeptree --reverse | grep numpy

# 冻结格式的依赖树（方便对比）
pipdeptree --freeze > tree.txt

# 提取仅顶层包（自动化清理）
pipdeptree --warn silence --freeze | grep -v "^\s"
```

**示例输出**：

```
fastapi==0.95.2
├── pydantic <2.0.0 [installed: 1.10.11]
└── starlette <1.0.0 [installed: 0.27.0]
pandas==2.0.1
├── numpy >=1.20.3 [installed: 1.24.3]
├── python-dateutil [installed: 2.8.2]
└── pytz [installed: 2023.3]
uvicorn==0.22.0
├── click [installed: 8.1.3]
└── h11 [installed: 0.14.0]
```

**识别规则**：不缩进的 = 顶层包（主依赖）；有缩进的 = 传递依赖。

**提取顶层包脚本**：

```python
import subprocess
def get_top_level():
    out = subprocess.check_output(["pipdeptree", "--warn", "silence"]).decode()
    return [line.split("==")[0] for line in out.splitlines() if not line.startswith(" ")]

for pkg in get_top_level():
    print(pkg)
```

## 四、pyproject.toml (PEP 621) 现代标准

### 4.1 基本结构

```toml
[project]
name = "movie-analyzer"
version = "0.1.0"
description = "达芬奇插件：视频分析工具"
requires-python = ">=3.10"
dependencies = [
    "fastapi>=0.100",
    "pandas>=2.0",
]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

### 4.2 迁移路线（requirements.txt → pyproject.toml）

| 步骤 | 动作 | 目的 |
|------|------|------|
| ① 依赖分析 | `pipdeptree --freeze` | 理清主依赖 vs 传递依赖 |
| ② 提取顶层 | 过滤出核心包，写 `requirements.in` | 只保留真正需要的 |
| ③ 验证重建 | 新建 venv，重装验证 | 确认行为一致 |
| ④ 现代化迁移 | `uv init && uv add --from-requirements requirements.in` | 生成 `pyproject.toml` |
| ⑤ 锁定 | `uv lock` | 生成 `uv.lock` |
| ⑥ 部署 | Docker 或 `uv sync` | 一致性交付 |

## 五、对我们环境的具体建议

### 5.1 当前状态诊断

| 问题 | 影响 | 建议 |
|------|------|------|
| 19 台 Mac 上 Python 3.9/3.13/3.14 混存 | 脚本跨机器运行结果不一致 | 以 3.13 为目标统一（Framework Python 已在 3 台机器就绪） |
| 达芬奇内嵌 Python 3.6 不受管 | 插件 subprocess 可能调错解释器 | 插件内必须用绝对路径或 sys.executable |
| 无依赖锁定机制 | 同一脚本在不同机器上装的第三方版不同 | 引入 uv/pip-tools 管理运维脚本自身依赖 |
| pip 全局安装 vs venv 隔离不清 | 包污染风险 | 运维脚本统一走 managed Python venv |

### 5.2 推荐策略

**运维脚本层（我们自己的工具）**：
- 使用 workspace 的 managed Python 3.12 (`~/.workbuddy/binaries/python/`) + venv
- 用 `pyproject.toml` 声明依赖 + `uv lock` 锁定
- 不触碰系统 Python 和 Framework Python

**达芬奇插件层（插件工坊管）**：
- 继续用达芬奇内嵌 Python 3.6 或 Framework Python 3.13
- 插件内必须 `include-system-site-packages=false`
- 依赖随插件分发，不假设全局可用

**集群统一层（未来）**：
- `install_python313.sh` 已覆盖新机部署
- 可考虑每台机器装 uv 后，用 `uvx` 运行无状态工具脚本

uv run python main.py                 # 执行
uv pip compile requirements.in > req.txt  # 兼容模式

# === 诊断 ===
pip list                              # 已安装列表
