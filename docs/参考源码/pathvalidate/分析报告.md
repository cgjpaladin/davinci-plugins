# pathvalidate 源码分析 — 与 sanitize_text() 对照

> pathvalidate v3.3.1, MIT, zero deps — 工业级跨平台文件名清洗库
> 2026-05-14 研读

## 对比矩阵

| 维度 | pathvalidate | 我们的 sanitize_text() | 差距 |
|------|-------------|----------------------|------|
| **Unicode 规范化** | 仅 filepath 模块做 | NFC 规范化（文件名） | 我们更好 |
| **控制字符** | 仅 ASCII 0-127 unprintable | \x00-\x1f\x7f-\x9f + Unicode零宽/BOM | 我们更全面 |
| **文件系统禁字** | 正则删除 `:*?"<>|` 等 | 全角替换(：？✱《》｜) | 我们更友好 |
| **Windows 保留名** | CON/PRN/AUX/CLOCK$/NUL/COM1-9/LPT1-9/¹²³ | CON/PRN/AUX/NUL/COM1-9/LPT1-9 | 缺 CLOCK$ 和上标变体 |
| **长度限制** | 按平台截断 (260/1024/4096) | 无 | ⚠ 缺 |
| **首尾清理** | lstrip(" ") → rstrip(" ") → rstrip(" .") | strip(' .') | 差不多 |
| **ANSI 转义序列** | 显式移除 | 无 | 文件名场景不需要 |
| **NTFS 元数据名** | $Mft/$LogFile 等（仅根目录） | 无 | 根目录才生效，低优先级 |
| **macOS 保留名** | : | 已替换为 ： | 已覆盖 |
| **警告系统** | 异常 + ErrorReason | tuple(cleaned, warnings[]) | 我们更好（用户友好） |
| **Null byte** | 显式处理 \0 | CONTROL_RE 覆盖 | 已覆盖 |

## 可以采纳的改进

### 1. 长度限制（优先级：高）
```python
_MAX_FILENAME_BYTES = 255  # macOS APFS/HFS+ limit

def _truncate_by_bytes(s: str, max_bytes: int) -> str:
    """按 UTF-8 字节数截断（保留完整字符）"""
    b = s.encode('utf-8')
    if len(b) <= max_bytes:
        return s
    # 从后往前找完整字符边界
    truncated = b[:max_bytes]
    while True:
        try:
            return truncated.decode('utf-8')
        except UnicodeDecodeError:
            truncated = truncated[:-1]
```

### 2. CLOCK$ 和上标变体（优先级：中）
```python
# 追加到 _WIN_RESERVED
_WIN_RESERVED.add("CLOCK$")
# 上标变体: COM¹/COM²/COM³, LPT¹/LPT²/LPT³
_WIN_RESERVED.update(f"{n}{s}" for n in ("COM","LPT") for s in ("¹","²","³"))
```

### 3. 首尾清理更精确（优先级：低）
```python
# 当前: strip(' .')  → 会删中间的 .  
# 改进: lstrip(' ') + rstrip(' .')  → 只删首尾
```

## 不建议采纳的

- **ANSI 转义序列移除**: 文件名场景不会出现
- **NTFS 元数据名**: 仅根目录，APFS 没有这个问题
- **平台自动检测**: 项目只跑 macOS，不需要 Windows/Linux 分支
- **fs_encoding 截断**: Python 3 utf-8 默认已处理

## 结论

我们的 sanitize_text() 在核心清洗维度（控制字符、禁字替换、警告系统）已经达到甚至超过 pathvalidate。
3 个可改进点：长度限制（最有价值）、CLOCK$保留名、首尾清理精度。
